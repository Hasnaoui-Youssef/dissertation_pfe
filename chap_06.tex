\section*{Introduction}
This chapter reports how the result was checked and what the checks established. It opens with the validation approach, which states the three settings in which a check runs and the rule that decides the setting for a given check. It then describes the bench, first the target device, the board, the probe and the trace components available on the target, then the languages, the build tools and the external software components. The instruction trace pipeline is taken first, in the order of the trace, and the conventional debug operations follow. A separate section covers the properties that belong to the engine as a whole rather than to any single capability. The chapter closes with the defects that appeared only against real hardware, the status of every requirement, and the limits of the result.

\section{Validation Approach}
\label{sec:test_strategy}
\label{sec:offline_tier}
\label{sec:ontarget_tier}
\label{sec:frontend_tier}
Validation is organized by capability, not by the machinery that exercises it. Each of the sections that follow takes one capability of the delivered system, states the requirement it discharges, and gives the evidence that the capability holds.

A check runs in one of three settings, and the setting is chosen by what the check needs rather than by what it covers. The first setting needs only the compiled engine and saved data: a recorded capture, firmware ELF files, and the trace-unit register values read once from a real device. The second needs the board, where a Python script sends the engine real debug-adapter requests over its input and reads the replies, so hardware behaviour is exercised with no person watching. The third needs the board and the VS Code extension, and checks what the developer sees on screen.

The rule followed throughout is that a capability is validated without hardware wherever the hardware adds nothing to the evidence. This is possible because the decoder and the reconstruction were written to run on a saved capture with no board attached, as Chapter \ref{ch:arch_n_impl} describes. A capture taken once becomes a test file that is replayed as often as needed, so the whole trace pipeline, apart from taking the capture itself, is validated off the board. The board is then reserved for what only it can show. Figure \ref{fig:test_tiers} gives the three settings.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\linewidth]{fig_test_tiers.pdf}
    \caption{The three settings in which a check runs, and what each one can exercise}
    \label{fig:test_tiers}
\end{figure}

Each check decides its own result. A check in the first setting is a small program that compares what it produced against a value written into it, then returns pass or fail. A script in the second setting passes when every reply and event it expects arrives, in the right order, with the right content. A check in the third passes when the view on screen matches what the engine sent.

No test framework is used. Each off-board check is a small program that verifies its own output and returns a code, which the build runs directly. This keeps the engine free of a dependency it would carry only for testing. Table \ref{tab:tests} in the annexes lists the checks and the capability each one serves.

\subsection{Microcontroller: STM32H7S3L8}
\label{subsec:target}
The main device used during the development period of the project is an STM32H7S3L8, a member of the STM32H7RS family. It carries an ARM Cortex-M7 processor \cite{cortexm7_trm} running at up to 600 MHz with a memory protection unit, a double-precision floating-point unit and separate instruction and data caches of 32 kilobytes each. The device provides 64 kilobytes of internal flash memory and 620 kilobytes of internal SRAM, and is supplied in a TFBGA225 package \cite{ds_h7s3}.

\section{The Instruction Trace Pipeline}
\label{sec:val_pipeline}
This section follows the trace from the components that produce it to the record the developer reads, and validates each stage of that path. It discharges FR1 to FR8 together with NFR1, the requirements that hold the contribution of the project.

\subsection{Configuring the Trace Components}
\label{subsec:val_config}
The engine has to find the trace source and the trace sink of the target and program them through the debug connection, which is FR1. What is checked is that the components the engine addresses are the components the device carries, and that the values the engine believes it wrote are the values the device holds.

On the board, the engine reads every identification register of the trace unit and each one is compared against a reference saved from the device. The reported core name has to be Cortex-M7. Naming a trace source that does not exist has to fail rather than fall back to an arbitrary component. Reading the registers back over the same connection that wrote them is what closes the loop: the configuration is not assumed to have taken effect, it is observed.

This check also serves the stage that follows it. The decoder cannot be set up from documentation alone, because it needs the exact ETMv4 configuration the device is running under. The register values validated here are the ones handed to the decoder, so an error at this stage would surface as a decoding failure rather than as a wrong result.

\subsection{Coupling Capture to the Run State}
\label{subsec:val_runstate}
\label{subsec:launch_check}
FR2 requires capture to start and stop with the run state of the program, with no separate command from the developer. The evidence is that a capture appears at a halt the developer did not ask to be traced.

On the board, the engine turns on the trace source and the sink, runs the processor for a moment, halts it, and the callbacks it receives are recorded. Exactly two arrive for each halt: a 16-byte synchronization marker that the extraction driver inserts, then the captured bytes. The marker is checked byte for byte. Section \ref{subsec:drivers} relies on this two-callback rule, and the rule is what makes an empty capture distinguishable from a missing one.

The same coupling is then exercised in a real session, shown in Figure \ref{fig:trace_check}. Trace is turned on, a breakpoint is set at \texttt{main.c:106}, and the program runs. When the breakpoint is hit the engine drains the trace and sends it, and the check confirms that the trace arrives before the stop is reported, so the record is complete by the time the developer sees the program stop. The program is then run a second time, and the second batch continues from where the first ended rather than starting over, which is the accumulation described in Section \ref{subsec:trace_lifecycle}. This check also confirms that the engine starts its own OpenOCD inside its own process, since no separate OpenOCD process exists while it runs.

The defect where trace was inconsistent and often empty, listed in Section \ref{subsec:field_issues}, was found here. Its cause was that the components were not armed on every transition that resumes the processor, which is precisely the property this check now guards.

\subsection{Extraction Over the Debug Connection}
\label{subsec:val_extraction}
FR3 requires the capture to be extracted over the same debug connection that carries every other debug operation, and NFR1 requires no hardware beyond the probe already on the board and no trace pins. These two are validated by the bench itself rather than by a dedicated check.

The bench of Section \ref{sec:hardware} carries the STLINK-V3EC embedded on the NUCLEO board and nothing else. No trace probe is attached, and no wire runs to the trace pins of the MIPI20 connector, which the four-bit trace port would otherwise require. Every result reported in this chapter, including every capture, was obtained on that bench. The extraction therefore uses the same serial wire connection as the register reads and the run control, and the requirement holds by construction of the bench on which the checks pass.

\subsection{Decoding the Captured Byte Stream}
\label{subsec:val_decode}
FR4 requires the extracted bytes to be decoded into trace elements. Decoding is checked apart from everything downstream of it, so a failure here cannot be mistaken for a reconstruction failure.

The check feeds the decoder a saved capture together with the exact ETMv4 register values read from the real trace unit, and confirms the bytes decode all the way through without the decoder rejecting them. No firmware is supplied, so nothing but the byte stream and the unit configuration is under test: the result is that the bytes become elements of the kinds listed in Table \ref{tab:elements}. Figure \ref{fig:offline_datapath} shows this stage and the ones after it, with the check that guards each.

\subsection{Reconstructing the Executed Instructions}
\label{subsec:val_reconstruction}
\label{subsec:offline_trace}
FR5 requires the sequence of executed instructions to be reconstructed from the elements and the program image. Reconstruction is validated in two ways: on data built by hand, where the expected result is known exactly, and on a real capture, where the result is compared against fixed numbers and against the firmware.

The hand-built checks use a small instruction table with no real firmware and no decoder, which is possible because reconstruction reads plain value types that depend on neither library. One builds three instructions, an \texttt{add}, a \texttt{bl} and a \texttt{bx}, feeds a range whose closing branch was not taken, and confirms that only the last instruction of that range is marked not-executed and that the mark does not leak into the next range. Another builds an inlined call chain and confirms that instructions from the same inlined line merge into one block, that instructions from different call chains stay in separate blocks, and that instructions in an assembly file never merge even when they share a line.

The whole pipeline is then run on one saved capture, with the capture, the firmware and the trace-unit registers kept as fixtures. The result is checked against numbers frozen on the first correct run: 114 executed instructions, 6 function blocks, and 2 start markers. Every reconstructed address has to exist in the firmware, which rules out a plausible but invented instruction stream, and at least one block has to carry a real function name. \subsection{Attributing Instructions to Source}
\label{subsec:val_attribution}
FR6 requires each reconstructed instruction to carry a function, a source file and a line. The attribution comes from a pass over the firmware ELF that records, for every address, the instruction bytes, its mnemonic and operands, whether it is a branch, a call, a return or an indirect jump, and the source file, line and inlined functions it came from. Every later stage reads these facts by address, so the pass is validated on its own before the reconstruction is trusted to use it.

Three ELF files are used. The first has no debug information; on it a \texttt{bl} has to be marked a direct call with its target address filled in, a \texttt{bx lr} has to be marked a return, and asking for an address in the middle of an instruction has to return nothing. The second is compiled with inlining forced on; on it one address has to unfold into its full inline chain, for example an instruction inside an inlined \texttt{add\_one} reported as \texttt{add\_one} called from \texttt{compute} at the exact line. The third is the real firmware from the board, and it checks the hardest case: guided by the mapping symbols of Section \ref{subsec:mapping_symbols}, the pass has to skip a literal pool sitting inside the code, running from \texttt{0x0800124C} to \texttt{0x08001264}, so those bytes are never disassembled as instructions. A real instruction just before the pool, at \texttt{0x08001214}, has to be decoded, and the first word of the pool must not be. Both addresses were read from the firmware's symbol table by hand before the check was written.

Attribution is then confirmed end to end. In the reconstruction of the saved capture, function blocks carry resolved names, and in the live session of Section \ref{subsec:val_runstate} the instructions arrive carrying real source lines with one block named \texttt{main}.

\subsection{Keeping Discontinuities Visible}
\label{subsec:val_gaps}
FR7 requires a discontinuity in the capture to be represented explicitly, with the two sides of it kept distinct. A gap is where the record is silent about what executed, and the failure mode to avoid is a record that reads as continuous across it.

Reconstruction counts the gaps and marks them, and the count is part of the frozen figures of Table \ref{tab:measured}: the traced interval contains two start-of-capture markers and no discontinuity within the execution itself. On the presentation side, the check on the view logic confirms that a gap is rendered as a plain separator and never as an instruction row, so nothing is displayed that the trace did not report, and the two sides of the gap remain separate as Section \ref{subsec:trace_lifecycle} requires.

\subsection{Presenting the Record During a Live Session}
\label{subsec:val_presentation}
FR8 requires the reconstruction to be presented inside a development tool during a live debug session, and NFR3 requires integration with existing development tools. The frontend is a VS Code extension that speaks the standard Debug Adapter Protocol, so the second requirement is met by the interface it uses rather than by an interface of its own.

The logic between the engine's messages and the views is checked in the editor's test host with no board, because a wrong result there would corrupt a view silently. A new batch of trace has to be appended to the list, a reset has to clear it, and a small reducer has to turn each state the engine reports, idle, capturing, decode error, and the rest, into the right message on screen.

The presentation itself is then confirmed on the board through the extension's real code path. A batch of trace produced in a live session has to reach the extension and fill both trace views. Figures \ref{fig:function_trace} and \ref{fig:instruction_trace} show both views filled from a live capture, the function view grouping the record by function and line, and the instruction view listing the executed instructions in order. These are the reconstruction of the preceding sections as the developer sees it, and they are the end of the path that began at the trace components.

The reconstructed instruction list was compared, line by line, against three commercial debuggers, each using its own vendor's probe. The lists matched, and the only differences were in how each tool printed them.

\section{The Conventional Debug Operations}
\label{sec:val_debug_ops}
Trace is only usable inside a working debugger, so the operations of FR9 to FR13 carry the same burden of proof. All of them touch hardware behaviour that saved data cannot reproduce, so all of them are checked on the board, with the parts that are pure computation checked off it.

\subsection{Run Control and Breakpoints}
\label{subsec:val_runcontrol}
FR9 requires the run control primitives of Section \ref{sec:primitives}. Two things have to hold for stepping: it has to stop, and it must never freeze when the chip runs out of hardware comparators.

The check steps over a call, into a call, and out of a call, and requires each one to stop within a set time. Stepping into \texttt{HAL\_Init} has to leave the top of the stack inside \texttt{HAL\_Init}, and stepping out has to leave it back in \texttt{main}. The time limit is what turns a freeze into a failing check instead of one that hangs forever, and it is what caught the defect where a step did not stop, listed in Section \ref{subsec:field_issues}. Its cause was that LLDB placed its internal step breakpoints in flash as software breakpoints, which never fire on this chip.

Breakpoints are exercised throughout: resolved on a source line in the trace check of Section \ref{subsec:val_runstate}, and resolved again through the extension in a check that also confirms that stepping over a call stops rather than hanging when driven through the same path a developer uses. Two of the defects of Section \ref{subsec:field_issues}, a breakpoint resolving into a vendor header at an inlined call site and breakpoints refused in assembly files, were found this way.

\subsection{Memory and Register Access}
\label{subsec:val_memory}
FR10 requires memory and processor registers to be read and written. On this chip memory is reachable through two access ports, one for the processor and one for direct memory access, so the requirement is not met by a read that returns bytes but by a read that returns the bytes of the port asked for.

The check reads the same address through each port and confirms the two differ, because on this chip they genuinely see that address differently. A read with no port named has to give the processor's view, the default. The same port read twice has to return the same bytes, which rules out a stale or a random result. Naming a port that does not exist has to fail. The difference between the two ports was confirmed separately with OpenOCD's own \texttt{mdw} command, so the check rests on an independently observed property of the device and not on the engine's own behaviour.

The memory view carries arithmetic that a wrong result would corrupt silently, and that part is checked off the board: address parsing, grouping bytes into 16-bit and 32-bit words in both byte orders, and dropping a leftover partial cell. Register access is exercised on the board along the same paths.

\subsection{Peripheral Inspection}
\label{subsec:val_peripherals}
FR11 requires the registers of a peripheral to be presented by name and by field from a description of the device. The description is the vendor's SVD file, and the check parses the file for the board's device and compares the result against fixed counts: 105 peripherals, 5\,902 registers, 25\,136 fields, and 30\,490 named field values. A peripheral defined as a copy of another, such as \texttt{ADC2} from \texttt{ADC1}, has to keep its own base address while inheriting its parent's registers. The exact bit position and width of one named field is checked. A register cleared by the act of reading it has to be marked, so a view never reads it by accident. The parser's memory use is recorded as well, since one device's description is large.

On the board, the engine's device model is read back, port \texttt{GPIOA} is read, and a scratch register in the backup domain is written and read back, chosen because writing it changes nothing on the board. Live watching is checked in the same run: the frames have to arrive with a strictly rising sequence number, and while the watch runs a register is written and no frame may carry a value read before that write finished. Figure \ref{fig:periprace} shows how that race is avoided. The field arithmetic behind the view is checked off the board: reading and writing one field without disturbing the bits around it, masking a value too wide for its field, and building the mask of a field that fills a whole 32-bit register without overflow.

\subsection{Disassembly and Variable Inspection}
\label{subsec:val_disasm}
FR12 requires disassembly and source-level inspection of variables. Disassembly is validated by the program analysis of Section \ref{subsec:val_attribution}, which is the same pass that serves the trace: for every address it yields the mnemonic, the operands and the class of the instruction, and it refuses to disassemble the bytes of a literal pool. Correct disassembly of the trace and correct disassembly in the view are therefore one property, checked once.

Variables and scopes are checked on the board, where they are requested at a stop and compared against the program that is running. The same property is checked again after a reset, described next, because that is the case in which it was seen to fail.

\subsection{Reset and Session Resynchronization}
\label{subsec:val_reset}
FR13 requires the target to be reset and the session restored to a state consistent with the reset device. Resetting the chip stops the processor by a path LLDB does not see, so afterward LLDB's picture of the program is stale. The resynchronization of Section \ref{subsec:reset_impl} repairs this.

The check resets the board, confirms the session reports a stop, then confirms that the stack and the variables reported afterward describe the program now running and not the one before the reset. The two defects where a restart left a stale view, listed in Section \ref{subsec:field_issues}, were found here, and the check is what distinguishes a reset that reached the device from a reset the debugger merely believes in.


\section{Properties of the Engine as a Whole}
\label{sec:val_engine}
Three properties belong to no single capability but would break all of them. They are validated separately, off the board, since none of them involves the device.

\subsection{Message Framing and Cancellation}
\label{subsec:val_protocol}
The engine and the editor exchange JSON messages, each prefixed with its byte length, and every capability of the preceding sections is delivered through that channel. A real \texttt{initialize} message is written to the engine's input and the reply has to be a proper \texttt{initialize} response advertising trace support. Passing this means the engine frames a message, parses it, routes it to the right handler and answers, all without a board and without the debugger library.

Cancelling a request was harder to get right, so it is checked on its own. The engine reads incoming messages on one thread and runs them on another, as Section \ref{subsec:concurrency} describes. The check sends a slow request that blocks, then a second request behind it, then a cancel for the second one, and requires the second request to come back marked cancelled with its handler never having run. This holds only if the reading thread can record the cancel while the running thread is still stuck on the slow request, so the check proves the two threads are truly separate.

\subsection{Event Delivery From Several Threads}
\label{subsec:val_eventbus}
Output is produced by several threads at once: the thread running debug requests, the thread receiving events from the debugger library, and the thread running OpenOCD. All of them hand their output to one object, the event bus, which passes each item to a single writer. If the event bus lost or duplicated an item under this load, output would be corrupted and every view fed by it would be wrong.

Three threads publish on the event bus at the same time, 2000 items each, and the output is counted with a plain counter that has no lock of its own. The count comes out right only if the event bus already holds its own lock while it delivers. The same check runs under a thread sanitizer, which flags a data race the moment it happens. Running the whole engine under that sanitizer against the board is how the lock-ordering bug of Section \ref{subsec:lldb_impl} was found.

\subsection{Host Portability and Process Integrity}
\label{subsec:val_portability}
NFR2 requires the engine to operate on Windows and on Linux. The same CMake build produces the engine on both, and the off-board checks run on both, so portability is demonstrated by the checks of this chapter passing on each platform rather than by a separate check.

One process-level hazard is checked directly. The engine links two copies of LLVM, one inside the LLDB library and one behind the disassembler, and two copies in one program can clash at startup, for example both trying to register the same command-line option. A build that only links proves nothing, because the linker pulls in just the code that is actually called. The check therefore calls into both, in the same order the real program does, and confirms that both start up and that the disassembler opens a firmware file. This catches the clash at startup, ahead of any debug session.

\section{Results}
\label{sec:results}
The objectives set in Section~\ref{sec:objectives} were met. Instruction trace is captured from an on-chip sink, read out over the ordinary debug cable, decoded, reconstructed into the list of executed instructions, tied to source locations, and shown inside a development tool during a live debug session. No trace pins and no special probe are used.

The debugger that carries this also provides breakpoints with automatic choice between software and hardware, stepping by source line and by instruction, variable and expression reading, memory reading and writing, disassembly, device reset, and the added views for trace, live memory, and peripherals. \section{Limitations and Future Work}
\label{subsec:limits}
\label{subsec:trace_limits}

The work meets its goals within limits, and those limits point to the next steps. The limits fall into two groups. Table \ref{tab:trace_limits_tab} gives the limits of the trace pipeline, the part that turns a capture into a reconstructed program. The limits of the engine that carries the pipeline follow the table, with the directions that extend the work.

\begin{table}[htbp]
    \centering
    \caption{Limitations of the trace pipeline}
    \label{tab:trace_limits_tab}
    \begin{tabularx}{\linewidth}{| @{}>{\hsize=0.75\hsize\bfseries}Y | >{\hsize=1.25\hsize}Y@{} |}
        \hline
        Limitation & \textbf{What it means} \\
        \hline
        Component discovery & The trace source and sink are found by name among the objects the configuration creates, and their base addresses are stated there. A new device needs a configuration file written for it. \\
        \hline
        One protocol version & The drivers and the decoder handle the version the devices used implement. No device reachable by the on-chip route is lost, since every STM32 device with an on-chip trace sink implements that version, as Table \ref{tab:stm32_debug} states. \\
        \hline
        One source and one sink & The first of each is used, so a device with several is not fully exploited. Tracing several cores is outside the scope of a proof of concept on a single-core target. \\
        \hline
        Timing discarded & Timestamps and cycle counts are decoded and then dropped, so no timing analysis is possible without changing that stage. \\
        \hline
        Exceptions not shown & The elements are kept and no view presents them, so an exception shows in the record as a jump in address. \\
        \hline
        No trace filtering & Tracing runs unfiltered, so the amount of trace is bounded only by the size of the buffer. On these devices filtering would be driven from the processor comparators. \\
        \hline
        Return classification & LLVM's analyzer does not recognize the instruction forms this architecture uses for a return, so those forms are matched on the printed text. \\
        \hline
        Off-board decoding not exposed & The stages need only a capture, a firmware image and the saved registers. The standalone entry point that offered this during development was not carried forward. \\
        \hline
    \end{tabularx}
\end{table}

Further limits concern the engine. The two disassembly paths have not been merged. A few requests drive LLDB outside the serialization of Section \ref{subsec:lldb_impl}. The capabilities that need the direct path are missing when attaching to an existing session. The frontend is not packaged for distribution.

Several directions extend the work. Keeping the timing elements now dropped would allow profiling from the same captures. Showing exceptions directly would complete the picture across interrupt entry. Turning on the trace unit's filtering would let the buffer cover a chosen region. Reading the component layout from the ROM tables would remove the per-device configuration file.


\section*{Conclusion}
This chapter has established that the result satisfies every requirement stated in Section \ref{sec:requirements}. The trace pipeline was checked one stage at a time, from the configuration of the trace components on the device to the record presented in the editor during a live session. The conventional debug operations were checked on the board, because their failure modes depend on the device and not on the data.

Two results stand apart from the requirements they satisfy. The reconstructed instruction list matched the output of three commercial debuggers line by line, each of those tools running on its own vendor's probe, and no check internal to the system can supply evidence of that kind. Every capture reported in this chapter was taken on a bench that carries no trace probe and no wire to the trace pins, which was the constraint the design was built around. The limits that remain concern the coverage of the result rather than its correctness, and each of them states a direction in which the work continues.
